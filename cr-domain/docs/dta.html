External lab data transfer (DTA / DTS)

Most of a modern trial’s data — safety labs, ECG, imaging, eCOA — is generated by outside vendors, not on your CRFs. Getting it from the vendor into your study database is governed by a Data Transfer Agreement (DTA) and its Data Transfer Specification (DTS). This page explains, in plain terms, how this reference makes that transfer set up once and reused — instead of hand-built per vendor, per data type, per study, and re-touched at every amendment.

The problem it removes

Today a DTA/DTS is a Word or Excel document. For every study, someone re-writes it for each vendor, and a programmer hand-maps that vendor’s columns to SDTM (LB, EG, VS…). The sponsor then assumes every one of those hand-built maps agrees — and every place they quietly disagree becomes a reconciliation query that surfaces late, near database lock.

For the study team / site manager

You stop rebuilding the same lab mapping every study. The vendor’s test names, units and visit labels are matched to your protocol once; the next study on the same vendor is already matched. Problems (a wrong unit, a visit label that doesn’t line up) are caught when the file arrives, not months later.

The CDISC 360i vision

This is the CDISC 360i Digital DTA goal made concrete: the DTS becomes a machine-readable contract generated from the USDM protocol, not prose. SDTM is rendered from it — never a stored target a human fills in. The “data validation & quality” work usually cut from an MVP (conformance, unit checks, visit reconciliation) is built in and runs at ingestion — the CORE / Dataset-JSON conformance the 360i roadmap calls for.

What the crosswalks do — three jobs

A “crosswalk” here is just a matching table the whole industry shares and keeps adding to. It does three jobs so a human doesn’t have to re-do them each study:

1

Match the vendor’s test to the standard concept

The lab calls it SODIUM; the standard concept is Sodium, identified by its LOINC code (2951-2). Match it once and it stays matched — and because the match is shared, the next sponsor using that same vendor term gets it for free. This is what replaces the per-study “encounter mapping” table that today is re-typed and stored inside every DTA.

2

Put units and visit labels on a common footing

The vendor sends mEq/L; the standard unit is mmol/L (UCUM), and the conversion is done for you, the same way every time — not a note in a spec. The vendor’s visit label V3 D29 is matched to your protocol’s Visit 3. Match a label once; every study that reuses it inherits the match.

3

Render the standard deliverables as output

Once a result is matched to its concept, unit and visit, the SDTM LB row, the Dataset-JSON, the Define-XML and the human-readable DTA document all come out as views. Nobody authors SDTM by hand; it is a rendering of the matched data.

What’s checked before the data lands

These checks run automatically at ingestion. This is the “quality” layer that a manual DTA leaves to a late human reconciliation pass:

SituationWhat happens
A test that isn’t matched to a standard conceptBlocked — it can’t be rendered to SDTM, so it isn’t admitted
A unit that isn’t a known standard unitBlocked — no safe conversion
A visit label that matches nothing and no one has confirmedBlocked
A file format or transfer method outside the agreed listBlocked
The person who signed off the transfer isn’t authorisedBlocked
A match the system is only somewhat sure ofFlagged for a person to confirm once — then it joins the shared library
Blinding scope not statedFlagged

The point of grading: a genuinely unusable transfer is stopped; a “probably fine, please confirm” is flagged, not stopped. A manual process can only do this with people and time; here it is built into the contract and runs on every file.

Who does what

  • DTA working group / standards owner — defines the DTS once (which data elements, which concepts, which units) and curates the shared matching library. New vendor terms get confirmed once and then compound.
  • Study team / data management — reuse the matched library; confirm the occasional unmatched term flagged at ingestion; read the SDTM / Dataset-JSON / DTA document as views.
  • Site manager — when a vendor’s visit label or unit doesn’t line up, it surfaces immediately as a flag to confirm — not as a query weeks later.
  • Imaging / eCOA and other ‘no standard code’ data — where there is no LOINC to match to, a clinician (e.g. the PI reviewing imaging on receipt) confirms the binding once; that attestation is a first-class part of the record, not an exception.
