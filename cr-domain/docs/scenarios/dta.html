External lab data transfer (DTA / DTS)

How outside vendor data — safety labs, ECG, imaging, eCOA — becomes clean, mapped study data, set up once and reused.

Most of a modern trial’s data is generated by outside vendors, not on your CRFs, and getting it into the study database is governed by a Data Transfer Agreement (DTA) and its Data Transfer Specification (DTS). Today both are Word/Excel documents, rebuilt per vendor, per data type, per study, and re-touched at every amendment — then hand-mapped to SDTM by a programmer. This page shows how that transfer becomes a machine-readable contract that renders SDTM automatically, and stops for a human only where it genuinely should.

The screen a manual DTA can’t give you. A central-lab file lands with a 10-analyte safety panel for one subject at Visit 3. Eight results resolve themselves to the standard concept, standardise their units, resolve the vendor’s visit label, and clear straight through — stored once, ready to render as SDTM on request. Two stop to be reconciled — one because the vendor’s term matched only weakly, one because it has no standard code at all — and wait for a single human confirmation. Confirm those two once and they never stop again: the match joins a shared library, and the next study on this vendor auto-resolves them. No programmer wrote a mapping.

How the screen is built

FHIR comes in; the data is stored as a graph. The lab’s FHIR feed is an exchange format, not a place to keep data. It is normalised once on the way in and stored as connected data (an NGSI-LD graph) — each result becomes a stored record carrying its identity, time, provenance, and resolution status. This screen, the SDTM LB dataset, Dataset-JSON and the DTA document are then all views over that one store — not re-parses of the original FHIR.

It’s all about provenance. Because the stored value is a transformation of the vendor feed — not the original — every element records where it came from: prov:wasDerivedFrom the original FHIR resource (kept and dereferenceable, so you can always trace back), prov:wasGeneratedBy the resolution step, and prov:wasAttributedTo the autonomous agent that resolved it, with its confidence. When a human reconciles, their confirmation is appended as another attribution — the machine step is never erased.

Resolve once, reuse forever. The vendor calls it SODIUM; the standard concept is Sodium (LOINC 2951-2). Resolve it once and the match is shared — the next sponsor on the same vendor gets it for free. This replaces the per-study “encounter mapping” table today re-typed and stored inside every DTA. Units (mEq/L→mmol/L, UCUM) and visit labels (V3 D29→Visit 3) resolve the same way.

Reconciliation is the only human step. Eight of ten analytes resolve on their own. The two that can’t — a weak match, and a biomarker with no code — surface as a reconcile call-to-action, confirmed once, then rendered. That is the “80% straight through, a small tail to confirm” the DTA demo shows, made real over the stored graph.

One NGSI-LD query to the broker assembles this screen — the normalised lab-file entity with every data element and its resolution status inlined. This hits the store, not the vendor’s FHIR API (that already came through and was normalised on ingest).

The stored cr:TransferFile entity — NGSI-LD, with @context (CR domain + W3C PROV), URN identity, and each data element inlined. This is a transformation of the vendor feed, not the source — so every value carries provenance: what it was derived from (the original FHIR resource, retained and dereferenceable), what generated it, and which autonomous agent resolved it, at what confidence. What’s checked before data lands

These run automatically at ingestion — the “data validation & quality” layer a manual DTA leaves to a late reconciliation pass:

SituationWhat happens
A test not resolved to a standard concept, with no confirmationBlocked — it can’t be rendered to SDTM
A unit that isn’t a known standard unitBlocked — no safe conversion
A file format or transfer method outside the agreed listBlocked
The person who signed the transfer isn’t authorisedBlocked
A match the system is only somewhat sure of (below threshold)To confirm — reconcile once, then it joins the shared library
A study-specific item with no standard codeTo confirm — a clinician confirms the binding once at the catalogue
Why grade it? A genuinely unusable transfer is stopped; a “probably fine, please confirm” is to reconcile, not stopped. A manual process can only do this with people and time; here it is built into the contract and runs on every file — and the reconcile tail shrinks every study as the shared library grows.

Two audiences, one mechanism

For the study team / site manager

You stop rebuilding the same lab mapping every study. Vendor test names, units and visit labels are resolved to your protocol once; the next study on the same vendor is already resolved. A wrong unit or an off visit label surfaces when the file arrives as a reconcile item — not months later as a query.

The CDISC 360i vision

This is the CDISC 360i Digital DTA goal made concrete: the DTS becomes a machine-readable contract generated from the USDM protocol, not prose. SDTM is rendered from it — never a stored target a human fills in. The validation & quality work usually cut from an MVP (conformance, unit checks, visit reconciliation) is built in and runs at ingestion — the CORE / Dataset-JSON conformance the 360i roadmap calls for.

Because every element is cleared, it projects 100% — the same way it projects to Dataset-JSON or Define-XML. Change nothing in the store; ask for a different view.
