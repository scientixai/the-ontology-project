Operator screen — Blood draw admissibility (OPP-101)

The impossible screen. A CRA reviewing the blood draw chain for Subject 423-MU07-018 at Visit 04 sees consent status, phlebotomist credentials, delegation log entry, protocol training record, vial specification, centrifuge calibration, chain-of-custody data logger, and carrier trace — all on one screen. Today each of these lives in a different point solution (CTMS, eTMF, LMS, LIMS, cold-chain logger, courier portal). One screen like this represents weeks of manual assembly. With TOP: one graph traversal.

Five point solutions, one screen. The blood draw admissibility view assembles data from: CTMS (consent status and subject enrollment), eTMF (delegation log entry), LMS (protocol and GCP training records), LIMS (vial specification, specimen receipt, centrifuge calibration), and the cold-chain logger and courier portal (chain-of-custody events from collection to lab receipt). Today a CRA manually collects these across five system logins; reconciliation for a single subject visit takes hours.

What TOP does differently. Every entity in this chain is a first-class node in the TOP graph. cr:CapabilityDelegation links the phlebotomist to their credential and training record. cr:InformedConsent is linked to the subject. The hcls:Specimen carries its custodyChain as a sequence of cr:CustodyEvent state transitions. A single join=inline&joinLevel=5 call traverses the entire graph and returns it in one response.

The innovation tax. Building this view from five point-solution APIs requires weeks of integration work per sponsor. The mapping is bespoke, brittle, and must be rebuilt every time a system is replaced. TOP makes the graph the integration layer — point solutions remain, but the connective tissue is standardized. A query that represents weeks of manual effort becomes a sub-200 ms broker call.
