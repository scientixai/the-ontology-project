Three layers, one coherent system

TOP is technology-agnostic by design. The same vocabulary is expressed in three complementary layers: each serves a different audience and can be used independently, but they compose into a single coherent system.

LayerArtifactWhat it doesWho uses it
OWL ontology
design-time spec		ontology/*.ttlDefines every class, property, and relationship. Enables OWL reasoning: if a cr:Delegation has a cr:delegatedCapability, the reasoner infers the person holds that capability. Machine-checkable axioms catch modelling errors before any data arrives.Ontology engineers, architects, tool vendors defining interop contracts
SHACL shapes
validation layer		shapes/*.ttlGraded constraints over instance data. sh:Violation = structural rules (a cr:Delegation without a cr:delegator fails GCP audit). sh:Warning = risk-proportionate rules (missing delegation log triggers a finding, not a hard stop). Runs in pySHACL, Jena, or any SHACL processor.Data engineers, QA, sponsor data management running validation pipelines
NGSI-LD entities
runtime substrate		dist/top-cr-v1.ngsi-context.jsonldJSON-LD over RDF. Every entity is an NGSI-LD entity; every property is a NGSI-LD Property or Relationship. The @context maps short names to OWL IRIs — so sponsoredBy in the broker is the same node as cr:sponsoredBy in the triple store. Scalable, REST-native, IoT-battle-tested (Scorpio, Orion-LD, FIWARE ecosystem).Application developers, integration engineers, context broker operators

The three layers do not require each other at runtime: you can run OWL reasoning offline, validate with SHACL at ingest time, and serve entities through the broker — or use any single layer alone.

Ingestion pipeline

A reference community runtime (AWS Garnet / Scorpio NGSI-LD CDK) ships separately. The canonical ingestion flow is:

Source                 Parse           Crosswalk              Emit
─────────────────────  ──────────────  ─────────────────────  ─────────────────────────
ICH M11 / USDM v4 JSON  → usdm→cr.py  → TOP cr-core entities  → NGSI-LD POST to Scorpio
Veeva DDA export (S3)   → odm→cr.py   → bulk catch-up load    → NGSI-LD batch upsert
Castor EDC (Kafka)      → edcstream.py → streaming ingest      → NGSI-LD PATCH (live)
Medidata Rave (API)     → rave→cr.py   → X_WHATEVER fields     → OperationalRecord + conf
eTMF (Veeva Vault API)  → tmf→cr.py    → TMF artefact types    → cr:Evidence subclasses

Every emitted entity carries the Universal DNA (top:identifier, top:observedAt, top:status) and is validated against the SHACL shapes before the broker accepts it. Sponsor-specific fields (X_WHATEVER) go into cr:OperationalRecord with an LLM-inferred cx:mappingConfidence score; a human reviewer promotes them to canonical mappings once confirmed.

The downstream stack serves three consumers simultaneously:

  • Scorpio context broker — REST/NGSI-LD queries for operational dashboards and EDC integrations (latency <50 ms, IoT-scale throughput)
  • Triple store (e.g. Apache Jena TDB2) — SPARQL 1.1 queries and OWL reasoning; receives every entity as N-Triples via the broker's notification stream
  • OWL reasoner (e.g. HermiT / ELK) — materialises inferred facts (capability delegations, protocol eligibility) and writes them back as asserted triples

Universal DNA

Every entity, whatever its category, carries three strands:

  • Identity — top:identifier: a stable, system-independent string key. In NGSI-LD the entity id is always urn:ngsi-ld:top-cr:{Type}:{localId}.
  • Time — top:observedAt: the NGSI-LD core observedAt term. Valid time — when this state was observed to hold in the world (ADR-0021 erratum; the transaction record is top:recordedAt). Always present, set at ingestion from the source's observation time.
  • Lifecycle — top:status: a named individual from the relevant codelist (e.g. cr:SiteStatusActive). Referenced by IRI so SHACL and OWL rules can reason over it, not just filter strings.

cr:UniversalDNAShape (the domain application of core's top:UniversalDNAShape) enforces all three on every entity. This is what makes any two TOP graphs line up by construction — before any domain-specific alignment.

Bitemporality (opt-in via top:Versioned): entities that record facts about the world (not just about the system) also carry top:validFrom / top:validUntil — when the fact was true in the world, independently of when the system recorded it. In NGSI-LD, Property-of-Property nodes carry both timestamps natively. cr:ProtocolVersion, cr:Enrollment, cr:Delegation, and cr:InformedConsent are all bitemporal.

The non-negotiable spine

  • Bitemporal by default: every assertion carries valid time (true-in-world) and transaction time (system knowledge); the past is reconstructable and back-dating is impossible.
  • Provenance on every fact: W3C PROV on every node — who asserted it, when, on what evidence, under which delegation. LLM-inferred mappings carry cx:inferredBy pointing to the autonomous agent that generated them.
  • PII containment: identifiable hcls:Person lives at the boundary only. Downstream logic attaches to the pseudonymous cr:StudySubject. The only legal bridge is the attested, bitemporal cr:Enrollment act — deliberately designed to be revocable and auditable.
  • Delegation invariant: every performed act (cr:Assessment, cr:Administration, …) links to the cr:Delegation that authorised it via cr:underDelegation. There is no performed act without an authorising delegation on record.
